## 1. 目的与范围

本规格说明书定义 Seeex 单公司管理系统的员工账号、组织部门、职级、RBAC、动态资源、企业微信认证、通讯录同步和事件回调需求。

系统可以独立运行；企业微信是外部身份、组织和职级数据源之一。当前范围是一个公司、一个固定租户上下文，不建设通用多租户能力。

本阶段不实现业务领域页面、RBAC 管理页面、动态菜单管理页面、角色继承、审批/打卡/消息等企业微信业务事件，也不把企业微信 Secret 写入前端。

## 2. 术语与概念

| 术语 | 定义 |
| --- | --- |
| 员工 | 系统内部人员主体，可来自本地创建或企业微信同步 |
| 员工账号 | 员工的登录凭证，与员工资料分离 |
| 外部身份 | 员工与企业微信等外部身份提供商的关联 |
| 角色 | 一组权限的集合 |
| 资源 | 可被授权的菜单、页面、Tab、按钮或 API |
| 菜单项 | 导航入口，引用资源但不等同于权限 |
| 职级 | 组织属性，可产生默认角色 |
| 数据范围 | 权限允许访问的数据边界 |

统一使用 **RBAC**（Role-Based Access Control）。

## 3. 用户角色与职责

| 角色 | 主要职责 |
| --- | --- |
| 普通员工 | 使用被授权的页面、按钮和业务 API |
| 部门负责人 | 作为组织属性参与部门范围判断，不自动获得管理员权限 |
| 系统管理员 | 管理员工、角色、资源、菜单和系统配置 |
| 组织管理员 | 处理部门、员工、职级和企业微信同步冲突 |
| 企业微信集成管理员 | 配置企业微信连接、发起同步、查看同步结果和重试失败事件 |
| 安全/运维人员 | 处理认证、事件解密和安全审计；解密操作必须记录审计 |

具体后台页面和操作授权将在 RBAC 设计阶段绑定到资源权限码。

## 4. 产品目标与成功标准

### 4.1 目标

- 让系统在没有企业微信时也能独立维护员工和 RBAC；
- 让企业微信员工自动进入系统并保留组织数据；
- 支持页面、Tab、按钮和 API 的分层授权；
- 支持全量同步、事件增量和失败重试；
- 保留可追踪、可审计、可恢复的组织和权限变化历史。

### 4.2 成功标准

- 本地员工和企业微信员工都能建立系统账号；
- 无角色员工可以完成认证，但进入无权限页；
- 企业微信重复事件不会重复创建员工、身份或自动角色；
- API 鉴权不依赖前端按钮显示；
- 离职员工不能继续登录；
- 权限、同步、认证和解密行为可审计。

## 5. 功能需求

### 5.1 员工与账号

**FR-EMP-001** 系统必须支持本地创建员工、企业微信同步创建员工和后续绑定外部身份。

**FR-EMP-002** 员工可以没有部门、没有企业微信身份，但仍可创建账号、分配角色并使用系统。

**FR-EMP-003** 员工状态至少包括 `ACTIVE`、`DISABLED`、`LEFT`、`LOCKED`；状态和账号登录开关必须分开保存。

**FR-ACC-001** 一个员工默认拥有一个主登录账号，员工资料和登录凭证必须分表保存。

**FR-ACC-002** 手机号作为默认登录标识，当前有效手机号在系统内必须业务唯一；手机号允许变更，变更不得改变员工、账号、角色、审计和外部身份关系。

**FR-ACC-003** 系统必须保留手机号变更历史或审计记录，并对手机号冲突进入人工处理。

**FR-ACC-004** 员工没有有效角色时，认证可以成功，但系统必须返回无权限状态，不得自动授予基础业务角色。

**FR-ACC-005** 员工进入 `LEFT` 状态后，账号必须禁止登录；历史记录不得物理删除。

### 5.2 企业微信身份与认证

**FR-WECOM-001** 系统必须使用独立外部身份记录保存企业微信 `userid`、`unionid`、姓名、手机号、邮箱、职位、头像和状态快照。

**FR-WECOM-002** 外部身份匹配顺序必须为：外部 ID、已确认手机号、创建新员工；多条匹配不得自动合并，必须进入冲突处理。

**FR-WECOM-003** 系统不得使用姓名作为自动合并依据。

**FR-AUTH-001** 系统必须支持企业微信 OAuth 和本地手机号/密码两种认证方式，认证方式由公司配置控制。

**FR-AUTH-002** 企业微信回调必须进入后端；后端负责验签、换取身份、匹配员工和生成本系统会话。

**FR-AUTH-003** 企业微信 Token 不得直接作为本系统会话凭证；本系统使用短时 Access Token 和可撤销 Refresh Token。

**NFR-SEC-001** `CorpSecret`、`Token`、`EncodingAESKey` 和 OAuth secret 不得出现在前端构建产物、浏览器存储或普通日志中。

### 5.3 组织与职级

**FR-ORG-001** 企业微信负责部门名称、层级、外部 ID 和负责人等组织主数据；系统负责本地排序、状态、权限关系和数据范围。

**FR-ORG-002** 员工可以属于多个部门，必须支持且最多只能有一个主部门。

**FR-ORG-003** 部门负责人只表示组织属性，不得自动获得管理员角色。

**FR-GRADE-001** 系统必须区分企业微信职位文本、企业微信原始职级和系统职级。

**FR-GRADE-002** 管理员可以维护外部职级到系统职级的映射；外部职级来源同时兼容企业微信独立职级接口和企业自定义字段；系统职级通过默认角色参与权限计算。

**FR-GRADE-003** 职级变化时，只能撤销由旧职级产生的自动角色，不得影响管理员手动角色。

### 5.4 RBAC 与资源

**FR-RBAC-001** 授权主体必须支持 `EMPLOYEE`、`DEPARTMENT` 和 `ROLE`；职级通过默认角色参与授权。

**FR-RBAC-002** 系统必须支持资源类型 `MENU`、`PAGE`、`TAB`、`BUTTON`、`API`。

**FR-RBAC-003** 每个受保护资源必须具有稳定的 `permission_code`，例如 `users:view`、`users:create`、`users:api:list`。

**FR-RBAC-004** 菜单项必须引用资源；同一页面资源可以被多个菜单引用；菜单可见性与页面/API 权限必须分开判断。

**FR-RBAC-005** 系统当前不实现角色继承。

**FR-RBAC-006** 有效权限必须按以下规则计算：

```text
ALLOW = 员工角色、部门角色、职级默认角色的有效权限并集
DENY  = 有效显式拒绝权限并集
FINAL = ALLOW - DENY
```

显式 `DENY` 优先于 `ALLOW`。角色绑定必须记录人工、职级、部门、企业微信或系统来源以及同步批次。

**FR-RBAC-007** 部门授权范围必须支持 `CURRENT`、`DESCENDANTS`、`CURRENT_AND_DESCENDANTS`。

**FR-RBAC-008** 前端按钮/菜单权限只负责展示；后端敏感 API 必须独立校验 API 权限。未登记 API 默认拒绝，公共接口必须显式白名单。

### 5.5 同步与事件

**FR-SYNC-001** 系统必须支持首次全量同步、事件增量同步和定时全量校准。

**FR-SYNC-002** 全量和增量必须复用同一套幂等 upsert 规则。

**FR-SYNC-003** 同步流程必须覆盖员工、外部身份、部门关系、职级映射和自动角色。

**FR-SYNC-004** 员工离职或被企业微信禁用时，系统必须将员工置为 `LEFT`、关闭登录并停用外部身份，不物理删除历史数据。

**FR-EVENT-001** 企业微信事件必须经过验签、解密、加密落库、幂等识别和异步处理。

**FR-EVENT-002** 事件处理必须支持重复去重、乱序容忍、失败重试、死信和人工重试。

**FR-EVENT-003** 原始事件永久保存但不得提供普通前端查看；受控解密接口的调用必须审计，解密结果只写入领域数据。

### 5.6 数据和审计

**FR-DATA-001** 主数据必须具备创建、更新和逻辑删除字段；逻辑删除使用 `deleted_at`。

**FR-DATA-002** 系统不使用 `version` 乐观锁字段。

**FR-DATA-003** 日志、员工、同步批次和事件业务编号使用日期+序列格式，例如 `2026111200000001`；数据库内部主键与业务编号分离；员工业务编号生成后不可直接修改。

**FR-DATA-004** 第一版必须实现数据范围模型，至少支持本人、本部门、本部门及下属、全部和自定义范围，并为业务服务提供统一的数据范围过滤入口。

**FR-AUDIT-001** 系统必须审计登录、锁定、手机号变更、身份绑定、员工状态、角色变化、资源/菜单变化、职级映射、同步重试、企业微信配置和事件解密。

## 6. 标准用例

### UC-AUTH-001 企业微信首次登录

| 项目 | 内容 |
| --- | --- |
| 参与者 | 员工、企业微信、认证服务 |
| 前置条件 | 企业微信配置有效，回调地址可访问 |
| 主流程 | 员工发起 OAuth；后端验签并换取身份；按外部 ID/手机号匹配；匹配不到则创建员工和账号；签发本系统会话 |
| 无权限分支 | 员工无有效角色时登录成功，进入无权限页 |
| 异常分支 | 多条匹配进入冲突状态，暂停自动同步，不自动合并 |
| 后置条件 | 登录、身份匹配和账号创建均有审计 |

### UC-SYNC-001 企业微信全量同步

| 项目 | 内容 |
| --- | --- |
| 参与者 | 组织管理员、同步服务、企业微信 |
| 主流程 | 创建同步批次；读取部门/人员/职级；幂等 upsert；同步关系；计算自动角色；记录结果 |
| 异常分支 | 单条失败继续处理并记录；批次可为 `PARTIAL`；失败可重试 |
| 后置条件 | 每条自动授权带来源和批次号 |

### UC-RBAC-001 权限判断

| 项目 | 内容 |
| --- | --- |
| 参与者 | 员工、权限服务、业务 API |
| 主流程 | 读取员工、部门和职级角色；合并 ALLOW；合并 DENY；执行 `ALLOW - DENY`；API 校验结果 |
| 异常分支 | API 未登记时拒绝；权限服务异常时不得默认放行 |

### UC-EVENT-001 事件失败重试

| 项目 | 内容 |
| --- | --- |
| 参与者 | 企业微信、回调服务、事件处理器 |
| 主流程 | 验签解密；保存加密原文；生成幂等键；快速响应；异步处理 |
| 异常分支 | 处理失败进入退避重试；超过最大次数进入死信；管理员可人工重试 |

## 7. 状态与错误规则

同步批次：`PENDING → RUNNING → SUCCESS/PARTIAL/FAILED`。

事件：`RECEIVED → PROCESSING → SUCCESS`，失败进入 `RETRY_WAIT`，超过上限进入 `DEAD_LETTER`。

标准错误响应必须同时提供：

```json
{
  "code": "USER_NOT_FOUND",
  "error_type": "NOT_FOUND",
  "error_message": "No user was found for the specified id"
}
```

权限失败使用 `AUTHORIZATION`；认证失败使用 `AUTHENTICATION`；同步业务冲突使用 `CONFLICT`。

## 8. 非功能需求

**NFR-PERF-001** 企业微信回调接口应在 3 秒内完成验签、落库并返回，不等待完整同步。

**NFR-PERF-002** 权限判断服务目标为 P95 小于 100ms；菜单/资源查询目标为 P95 小于 200ms（不含网络传输）。

**NFR-REL-001** 同一事件重复投递多次只能产生一次有效业务变更。

**NFR-REL-002** 同步失败不得导致已存在的员工账号被误删除或误授权。

**NFR-SEC-002** 权限服务、回调服务或身份匹配失败时默认拒绝，不得默认放行。

**NFR-SEC-003** 日志中不得输出 Secret、AESKey、密码、完整手机号或事件明文。

**NFR-DATA-002** 手机号唯一性必须由数据库对有效账号和服务层共同保证；逻辑删除或历史手机号不得阻塞合法的新绑定，但历史记录必须保留。

**NFR-AUDIT-001** 所有授权变化、同步结果和受控解密操作必须可以按操作人、时间和对象追踪。

**NFR-DATA-001** 事件原文永久加密保存；审计日志追加保存；主数据默认逻辑删除。

## 12. 需求追踪与后续设计

需求进入设计时，按以下关系追踪：

```text
FR-EMP/ACC → employee、employee_account、认证服务
FR-RBAC → role、resource、assignment、PermissionService
FR-WECOM → 外部身份表、WeComAdapter、OAuth 服务
FR-SYNC/EVENT → sync_run、sync_event、同步状态机
FR-DATA/AUDIT → 通用字段、序列生成器、audit_log
NFR-SEC → Secret 存储、API 鉴权、日志脱敏
```

后续设计顺序：数据库 ER/SQL、RBAC 权限服务、企业微信适配器、同步状态机、认证与回调 API Contract，最后再设计管理页面和业务页面。

## 13. 已定稿的设计约束

- 员工业务编号由系统生成，创建后不可直接修改；如需展示别名，应增加独立展示字段，不覆盖业务编号。
- 当前有效员工账号的手机号必须业务唯一；手机号变更通过历史表和审计记录追踪。
- 企业微信职级接入层兼容独立职级接口和企业自定义字段，统一映射到系统 `job_grade`。
- 员工授权和部门授权使用统一的多态角色绑定模型，通过 `subject_type` 区分主体。
- 第一版实现数据范围表和统一过滤入口：`SELF`、`DEPARTMENT`、`DEPARTMENT_AND_DESCENDANTS`、`ALL`、`CUSTOM`。
