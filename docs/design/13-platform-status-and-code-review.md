## P1 组织调整可间接授予超出授权范围的角色

触发：操作者只有员工修改权限和本人/部分员工的数据范围；某个有效职级绑定高权限默认角色。更新员工部门关系时可以直接指定该职级ID，后端只验证部门范围及职级有效性，没有校验操作者是否有权授予该默认角色。权限计算随后直接继承职级默认角色。

类似地，修改职级默认角色的入口只要求 job-grades:update，没有独立的可授予角色限制。这是确定的权限分离缺口，不表示无权限匿名用户能够直接利用。

证据：

- `seeex-tech-backend/web/src/main/java/com/seeex/tech/web/organization/OrganizationController.java:66`，员工修改入口。
- `.../organization/OrganizationManagementService.java:275`，职级有效性检查与保存；`:230`，默认角色写入。
- `.../rbac/PermissionService.java:132`，职级默认角色加入权限来源。

建议：把部门/职级等普通资料变更与隐含角色授予分开判断；对默认角色和员工职级变更执行可授予角色范围校验，禁止仅凭员工编辑权限给自己提权。补充最小权限账号修改自身职级的拒绝用例。

## P1 全量同步中单个员工失败可能提交残缺部门关系

触发：远端成员包含本地尚未映射的某个部门。upsertEmployee先修改员工、删除原部门关系，再逐项检查并插入新关系；中途遇到缺失部门抛异常。该私有方法没有独立事务，外层全量同步捕获异常继续，异常没有退出整个事务，先前删除/部分插入可能随批次提交。

结果：虽然页面显示PARTIAL，员工关系和继承权限可能已经被部分改写。新增员工也可能留下未完整初始化的记录。

证据：`.../wecom/WeComSyncService.java:156` 删除关系、`:159` 才验证部门，`:71` 捕获失败继续；外层事务位于`:47`。

建议：先完整解析/验证所有目标部门、映射和成员字段，再写入；每个员工通过独立受代理事务处理，失败回滚该员工整组修改。远端HTTP读取放在数据库写事务外，并持久化失败成员明细。

## P2 全量批次缺少进程中断后的恢复

领取动作将PENDING改为RUNNING后直接执行同步；调度查询只取PENDING，没有RUNNING租约、心跳或超时回收。进程在领取后退出，旧批次可永久停在RUNNING。事件消费者虽有超时回收逻辑，全量批次没有对应机制。

证据：`.../wecom/WeComSyncWorker.java:17` 至`:20`。

建议：批次增加lease/heartbeat/attempt与执行令牌，恢复时使用CAS及fencing避免旧worker覆盖新结果；提供明确重试入口。

## P2 权限策略和范围配置缺少并发版本保护

两个管理员读取同一策略后分别提交，保存只按ID更新，没有row_version/expectedVersion，后提交的旧表单会覆盖先提交的效果、状态或数据范围。角色范围使用delete+insert替换，也没有客户端版本冲突检测。

证据：`.../governance/ApplicationGovernanceService.java:57` 至`:62`；`.../rbac/RoleDataScopeController.java:39` 至`:42`；V22策略表没有版本列。

建议：添加乐观锁及expectedVersion，旧表单返回409，显示实际差异后重新确认；应用管理员整体替换也应使用同一规则。

## P2 列表和审计导出存在明确的逐条查询规模风险

组织、角色和权限计算内多次按人员/部门/角色逐项读取；审计列表与导出逐行查询操作者，10000行导出可能产生约10000次名称查询。审计筛选字典和应用治理选项还会全量读取。静态可以确认查询模式，但本次没有测试实际延迟或容量。

证据：`.../audit/AuditService.java:82`、`:96`、`:106`；`.../rbac/RbacManagementService.java:447` 的角色统计；`.../governance/ApplicationGovernanceService.java:69` 的字典读取。

建议：批量查询与请求内映射缓存，异步名称搜索/分页字典；审计导出使用批量操作者映射并保持原有行数限制和权限过滤。

## 企业微信同步事务整改边界

用户补充要求：同步必须考虑事务。该项列为P1，以下是后续整改约束，当前尚未修改同步实现。

1. 全量编排不包一个长事务；企业微信HTTP读取、重试与预览均在组织写事务外，避免等待网络时持有数据库锁。
2. 部门树先完整校验父级/循环/映射，再在短事务中完成两遍写入；失败整体回滚本次部门树，不能提交半套父子关系。
3. 员工通过独立Spring Bean公开方法执行REQUIRES_NEW事务。资料、主部门、所有部门关系、职级和同步版本必须同进同退，先校验完整目标集合，再替换关系。不能只给同类private方法加注解。
4. 外层捕获员工事务回滚后的异常，记录该员工失败并继续其他员工；成功数仅在代理方法提交成功后累计。批次可PARTIAL，单员工不允许部分成功。
5. 批次领取、心跳、失败明细和最终状态使用独立短事务；失败状态不会跟随员工事务一起回滚。处理进程崩溃时通过租约及执行令牌回收，旧worker不得覆盖新执行结果。
6. 增量事件的组织写事务与全量复用同一员工原子写服务；事件状态成功只能在业务写提交后记录，重放不产生重复关系或旧数据覆盖。
7. 回归至少覆盖：替换关系后中途失败、非法部门/职级、数据库唯一键失败、单人失败其他人成功、提交前崩溃、提交后状态更新前崩溃、批次重试和并发全量/增量。

事务重构与职级授权边界应先于新增审批业务实施；本轮依然只做静态复核，不运行事务测试或数据库操作。
